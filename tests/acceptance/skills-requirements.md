# Skill management user outcomes

Issue: https://github.com/openkursar/hello-halo/issues/502

This records the 27 product stories and rules A–F confirmed for local implementation. It is a requirements reference, not an implementation report, an executable binding, or a semantic-hash human approval record. New scenarios remain planned until actual bindings exist; documented expectations do not imply verified behavior.

## Storage and shared rules

User-created, manually imported, AI-written and existing project skills are files: global `~/.agents/skills/<name>/`, workspace `<working-directory>/.agents/skills/<name>/`. Existing home/current-workspace `.claude/skills` and previously readable legacy skill/command formats remain readable without rewriting. Store, bundled, built-in and digital-human dependency skills live in the same folders; Halo keeps no private skill folder, and files outside the supported folders are not automatically activated. A skill of the same name already standing in the folder is the user's and is never replaced. Halo's install record only remembers origin, version and what Halo last wrote, so an author update never overwrites files the user changed elsewhere. UI grouping and storage location are different: a personally installed store skill belongs to My skills.

Files or installed package content are authoritative, not an old database instruction body. Before a legacy installation has successfully migrated to file authority, however, its complete saved package is recoverable even when the former generated directory is missing; that absence is not a user deletion. Import and copy produce independent complete copies; scope change moves one complete resource. No arbitrary linked-folder feature, per-person allowlist, multi-workspace binding, persistent watcher, background polling, historical usage scan, plugin distribution or new long-lived recycle system is added. Every engine uses the same skills: Halo SDK receives the effective catalog, Claude Code receives the skills outside its own folders through one Halo-owned directory of links, and engines that read the shared folder themselves find them there. No engine shows a compatibility notice, and Halo does not change engine settings or add compatibility tables to the everyday library.

## Confirmed interaction refinement

The confirmed issue 502 correction improves the existing experience rather than freezing the old UI or replacing it with technical inventory screens. These refinements clarify the existing stories below; they do not add another product-story or variants matrix, and they do not create a human approval record.

- Cards keep quick enable/disable, More, scope pills and version/update information while retaining the source groups. Ordinary lists show neither engine tables/technical engine warnings nor raw paths, filesystem exceptions or copy counts. A local failure offers a concise next action without hiding healthy skills.
- Detail retains the author/version/update and scope header, Use, description and instruction/editor hierarchy. Other versions stays collapsed until requested. Scope changes use a popover, not a permanently visible select. More holds new conversation, custom copy and refresh.
- Card and detail mutations share behavior: ordinary enable/disable needs no confirmation; disabling a workspace copy that exposes an enabled global version requires its fallback explanation and confirmation. Delete asks once, identifies the selected skill and explains Trash/supporting-file impact; a raw disk path is not mandatory in every confirmation. Save keeps its confirmation.
- Closing More by its toggle or Escape creates no conversation. Explicitly selecting Use in a new conversation creates the intended conversation directly, without a redundant confirmation or automatic send; ongoing conversations are not interrupted.
- A digital human's skill row is named for the skill, expands inline instructions first and then offers Open skill detail. The row is not a raw-path label, and supporting content remains lazy-loaded.

## Verification boundaries

Preserve existing draft, cancel, custom-copy, scope-move/conflict, override/fallback and actual invocation scenarios in `capabilities/skills.yaml`. Its former disable-withdraws-files and uninstall/reinstall lifecycle is superseded by file-preserving disable and single-confirmation trash. Cancel evidence belongs to actual confirmation or menu boundaries, not an invented ordinary-toggle or new-conversation confirmation. Executable confirmation selectors use the real `alertdialog` role; editor and detail dialogs retain their actual roles. CLI migration must not recreate skill ownership under the engine configuration directory.

`capabilities.skill-upgrade.legacy-db-only` is a narrow planned app-e2e smoke, not an expansion of the 27-story variants matrix. Its fixture must prepare old saved records before the first launch, including the erroneous version 1 missing-files marker and a paused package, then exercise recovery, restart and deletion after successful migration. It remains without real-application binding until that journey executes with actual persisted files and controls; migration unit tests and current-version installs after startup cannot stand in for it.

Required coverage spans global/workspace, created/imported/discovered/store/dependency/built-in, single/text/binary resources, enabled/disabled/conflict/missing/unreadable, directory/link/cross-volume, cancellation/failure/retry/concurrent change, all new execution entry points and old sessions, upgrade/retry. Use isolated HOME/user profile/Halo data and synthetic resources, never real personal files, credentials, conversations or projects. Unsupported environment, manual trash/cross-volume checks and absent bindings remain explicitly unverified. macOS, Windows, Linux and remote evidence are separate; one platform/engine cannot establish another.

Scripted-model evidence must observe the real application's SDK listing, Skill tool, command expansion and collaborator requests; fixtures must not insert skill instruction bodies directly. It proves propagation, not a live model's guaranteed selection or obedience. Actual execution requires current controlled build identity and findings/evidence-integrity checks; catalog validation and doctor do not prove user journeys.
