# Acceptance assets

The catalog describes user outcomes independently of the implementation. Source
assets are versioned; reports and execution evidence are outputs, never inputs to
the expected behavior. No catalog entry is treated as human-approved by discovery.

## Files

- `catalog/<module>/module.yaml`: module ownership, supported scope and change paths.
- `catalog/<module>/<story>.yaml`: a user story, promises and verification scenarios.
- `contracts/<capability>.yaml`: reusable promises and scenarios.
- `approvals/*.json`: explicit human decisions tied to the semantic content hash.
- `schemas/`: machine-readable contracts for these records.
- `output/`: ignored plans, manifests, immutable run records and the rendered handbook.

## Catalog format

Every source record has `version: 1`. Human-readable text is an English string
or an object with `en` and optional `zh` translations. Translations share the
same record; identifiers and execution metadata are language-independent.
A module has `id`, `title`, `description`,
`paths` (repository-relative glob patterns), `dependsOn` (module ids) and `scope`
(a prose statement of supported roles, entry points, platforms and recovery).

A story has `id`, `module`, `title`, `story`, `basis` (one of `documented`,
`observed`, `proposed`), `references` (repository-relative sources), `promises`
(a mapping of stable promise ids to text), and `scenarios` (an array). Optional
`uses` entries reference shared contracts with `{ contract, scenarios }`; the
imported scenario id is prefixed with the consuming story id. Optional `questions`
are unresolved product decisions, not implied requirements.

A contract has `id`, `title`, `promises` and `scenarios`, with the same definitions
as a story. Story-specific scenarios may override imported scenarios only through
an explicit `overrides` entry; silent duplicate ids are invalid.

Each scenario has `id`, `title`, `verifies` (promise ids), `platforms` (`darwin`,
`win32`, `linux`), `profiles` (`fast`, `regression`, `live`, `external`), `evidence`
(`ui`, `app-e2e`, `integration`, `live-model`, `external`, `manual`), `mode`
(`none`, `scripted`, `live`), and `automation` (`automated`, `planned`, `manual`).
`manual` requires `reason`; `planned` remains in coverage even without a binding.
Optional `variants` is a mapping of dimension names to nonempty string arrays;
it expands required execution instances, not prose or operation scripts.
Optional `requirements` lists machine/environment prerequisites. Optional
`notes` explain coverage selection or limitations. Optional `preconditions`,
`steps` and `expected` are arrays of natural-language text, not executable
instructions. These conditions, steps and outcomes, together with scenario titles,
promises, platforms, variants, notes and exclusion reasons, enter the semantic
hash. A `verifies` entry must refer
to a local promise or a qualified imported promise (`contract-id.promise-id`).
Execution metadata (`profiles`, `evidence`, `mode`, `automation`, `requirements`)
is excluded from the product semantic hash; changing it still invalidates the
catalog and any saved execution plan.

## Executable bindings

Tests declare an `acceptance` annotation whose description is a JSON object:

```json
{"caseId":"teams.keep.members","evidence":"app-e2e","mode":"scripted","variant":{}}
```

`caseId` is globally stable. Catalog scenarios use complete ids; imported scenarios
use `<story-id>.<contract-scenario-id>`. A test binding states its actual boundary;
a UI test with replaced application handlers is `ui`, not `app-e2e`. A scripted
model substitutes the model endpoint while retaining real application logic.
Each required variant needs its own binding and result. A test may declare
multiple annotations only when it independently asserts every referenced outcome.

The manifest is generated by test-runner discovery, never a second hand-maintained
binding list. Unknown cases, unsupported variants and conflicting boundaries fail
validation. Backend/cluster executors report the same binding contract through
an adapter. Discovery is not execution and cannot establish a passing result.

## Results and decisions

Every run records a unique id, timestamps, code revision, catalog hash, test
manifest hash, platform, selected cases, execution mode and evidence paths. Each
case instance records its actual attempts and one result: `passed`, `failed`,
`flaky`, `skipped`, `blocked`, `not-run` or `manual`. Missing results are `not-run`.
Test-runner failure cannot be converted into a passing empty report. Historical
results cannot be reused against changed expectations or silently overwritten.

Run version 1 may also include `executionBatches`. Each batch identifies its
selected test ids, executor, model mode, execution configuration, timestamps and
terminal state. Its `executionHost` names `source`, `packaged` or `cluster`, the
controlled `buildId`, and an optional supplied `packageId`. Attempts carry the
same configuration and `batchId`. These fields record what the runner supplied,
not what an application actually launched; app and engine observations remain
test evidence. Older records without these fields show the configuration as
unrecorded, even when the run has a top-level package identity.

The run's `evidenceIntegrity` record has `version: 1`, `valid` and `reasons`.
It records whether source/build identity and runner-level checks remained valid.
If those checks fail, otherwise passing cases become `not-run`, with raw attempts
retained for diagnosis. A report requires a valid integrity record without reasons
or run-level errors before counting a case as verified. Older runs lacking this
record remain readable but cannot supply current verification.

Human approval and verification are independent. Approval stores the story id,
the exact semantic hash, decision, timestamp and human-supplied reviewer name.
Approvals are created only by an explicit human action. Changes to promises,
scope, conditions or exclusions invalidate approval; implementation-only binding
changes require revalidation, not a new product decision.

## Operation

The harness exposes `validate`, `catalog`, `build`, `package`, `discover`, `plan`,
`run`, `report`, `doctor` and `decide`. Plans accept a profile, modules, explicit
cases or a Git change range.
Unmapped changes and shared infrastructure changes expand selection conservatively.
Nightly plans use the previous successful validation baseline and a resolved target
commit. A branch name alone is not a build identity. Live-model and external runs
are opt-in and bounded; missing prerequisites remain visible in the report.

Application runs require a controlled `build`: it records product inputs before
and after the real build, compiled artifacts and the independently installed SDK.
Build provenance uses `version: 2` and names the generated outputs cleaned before
building: `out/main`, `out/preload`, `out/renderer`, `resources/api-ref`,
`resources/builtin-apps`, `resources/office-runtime` and `resources/dsh-runtime`.
An exclusive lock prevents concurrent controlled builds; verification refuses
an in-progress build or a stamp without this clean-output guarantee.
`run` verifies that identity before and after execution. Merely finding an old
application under `out` is insufficient, and a source manifest cannot attest
which application binary was actually exercised.

`package` creates a directory application for the current host without publishing.
Its provenance records packaging inputs, the controlled build, byte comparisons
for the application outputs and SDK runtime, and the complete emitted bundle hash.
That identity is distinct from a passing packaged-app test. Platform-specific
dependency pruning, installer behavior and release signing are not inferred from
the provenance record.
